日期：2026-10-21。对应 [方案 B](Search_Storage_B.md) 和 [迁移兼容契约](Library_Migration_Compatibility.md)。

## 2. 实测容量

GB 使用 10^9 字节，GiB 使用 2^30 字节；文件属性中约“18 GB”的来源库实际为 19.50 GB / 18.16 GiB。

| 变体 | 文件字节数 | GB | 处理 |
|---|---:|---:|---|
| 冻结基线 | 19,495,989,248 | 19.496 | 原结构、原索引布局 |
| 旧结构整理对照 | 18,941,419,520 | 18.941 | SQLite 3.54.1，FTS optimize + VACUUM INTO |
| B 整理前 | 10,612,297,728 | 10.612 | 真正移除六个业务派生列，重建 FTS 后 |
| B 最终候选 | 10,498,117,632 | 10.498 | optimize + VACUUM INTO |

相对原库减少 **8,997,871,616 字节，46.15%**；相对同样整理过的旧结构减少 **8,443,301,888 字节，44.58%**。单纯整理旧库只节省约 0.555 GB，因此主收益不是碎片整理。

`dbstat` 进一步拆分如下（GB，统计名称以 `audio_search` 开头的 FTS shadow btree）：

| 变体 | `audio_files` 占用 | FTS 占用 |
|---|---:|---:|
| 原库 | 16.755 | 1.896 |
| 整理后的旧结构 | 16.276 | 1.892 |
| B | 7.830 | 1.895 |

倒排索引本身基本保持原大小，节省的是业务行中的派生文本。最终候选和整理对照的 freelist 均为 0；三份只读测量文件均无 WAL/SHM/journal sidecar，不存在只比较主文件而漏计候选 WAL 的情况。

候选约 **9.78 GiB**。没有使用紧凑字对 rev 4，没有取消原始列索引，也没有减少 `detail` 或关闭文档长度。不能把 Grok 对紧凑编码的 5–6.5 GB 估算继续叠加到这个结果：方案 B 已移除其主要优化对象——业务表里持久化的分词字符串。

全库重新生成的六列分词文本共 **8,393,843,191 字节**。此前名称为 `bwf_description_tokenized` 的大列实际上还承载公开源 Metadata 的搜索投影，不能只按 BWF description 的长度估算。

## 3. 数据与检索一致性

下列检查均已通过：

- 909,342 条记录逐行重新生成六列 rev 3 投影，与原库保存文本逐列比较，差异 **0**。
- 12 张业务表按稳定键、SQLite 值类型和实际值计算 SHA256，全部一致。仅排除明确移除的六列和新增的 `search_storage` feature；原始 Metadata JSON、用户标注、历史、ID、目录和引用全部参与。
- 909,342 份 FTS `docsize` 相同；文档总数、各列 token 总量的统计块相同。
- `fts5vocab` 的 **1,198,133** 个词项，逐项比较 term、文档频次和出现次数，摘要相同。
- 原库/候选 `PRAGMA integrity_check` 均为 `ok`，`foreign_key_check` 均无异常；构建、整理及修改流程中的 FTS 完整性检查通过。
- **58 个文本查询**在同一 SQLite 3.54.1 引擎下比较原库/候选的完整命中 ID 集合和每个命中的原生 BM25 位模式，全部相同，不限于第一页。覆盖高命中 `ex`、常见词、组合词、无命中、中文、Unicode folding、组合字符、数字、标点和看似操作符的普通文本。
- 候选自定义 BM25 与原生 BM25 对全部上述命中记录比较，实际最大差异 **0 ULP**（测试允许上限 2 ULP）。
- 四个变体各 **86 个 DataProvider 场景 × 3 轮**，返回 DTO 所有业务字段、顺序、分页 ID、准确总数及目录统计一致；以原引擎基线作参考，共 **774 次跨变体逐场景比较**。

这不是对全部可能查询的穷举证明。中文命中较少，播放列表/项目引用/Waveform 表在本样本为空；保留空表不等于验证了复杂非空引用迁移。

## 4. 查询性能

计时范围为 `DataProvider.search` 完成准确计数及结果 hydration；另测 `search_folders`。表中的“合计”是两次顺序调用耗时之和，不是 GUI 并发调度后的可见延迟。P95 按样本排序后 nearest-rank 计算，不把两个 P95 相加。

86 个场景包括 58 个文本查询、空查询、六种双向排序、三个深分页、六种筛选及有/无子目录的目录查询。每组连续三轮，首轮 86 个样本，后两轮 172 个样本；“重复”仍是混合负载，不假设每次都命中应用缓存。

| 变体 | 首轮搜索 P50 / P95 ms | 首轮合计 P95 ms | 重复搜索 P50 / P95 ms | 重复合计 P95 ms |
|---|---:|---:|---:|---:|
| 原结构 / SQLite 3.53.2 | 73.3 / 345.5 | 512.7 | 71.1 / 366.1 | 551.4 |
| 原结构 / SQLite 3.54.1 | 73.3 / 377.0 | 537.2 | 69.4 / 342.8 | 531.8 |
| 整理后的旧结构 / 3.54.1 | 65.7 / 372.8 | 548.3 | 58.9 / 289.1 | 424.0 |
| 方案 B / 3.54.1 | 68.5 / 344.6 | 508.7 | 48.8 / 246.6 | 377.4 |

候选在本次重复混合负载中的搜索 P95 比原引擎基线低约 32.7%，比整理后的同引擎旧结构低约 14.7%。这是本机该次负载的观测，不是所有查询或硬件的固定加速比。

58 个普通文本查询首轮，B 的搜索 P95 **231.3 ms**、合计 P95 **258.7 ms**。但扩展到所有排序/筛选场景时，首轮合计 P95 仍为 **508.7 ms**，不能宣称所有场景满足 500 ms。

**长尾保留：** B 首轮 `metal` + 1–10 秒时长筛选出现搜索 **5,356.2 ms**、合计 **5,579.5 ms**；部分排序也超过 1 秒。原引擎基线同一时长筛选约 899.0 ms，标签排序约 906.8 ms。原始异常值已保留，后续重复测量不能从首轮统计中删除它们。

另取 12 个文本/空查询，每个场景单独启动进程，轮换原引擎基线、整理后的旧结构和 B 的执行顺序。三组的首次搜索最大值分别为 **304.6 / 299.1 / 301.3 ms**，加目录统计最大值为 **339.2 / 330.5 / 333.4 ms**，结果全部一致。这组只有 12 个场景，不能代替完整混合负载。

对六个慢场景再分别执行三轮新进程复核，三种变体共 54 次，结果仍全部一致。以下是“搜索 + 目录统计”的三次中位数；排序保留原请求的方向和分页：

| 场景 | 原引擎基线 ms | 整理后的旧结构 ms | B ms |
|---|---:|---:|---:|
| `metal`，时长升序 | 359.2 | 359.9 | 364.7 |
| `door`，时长降序、offset 200 | 111.3 | 106.1 | 100.0 |
| `metal`，采样率升序 | 450.8 | 434.1 | 426.4 |
| `metal`，修改时间升序 | 477.0 | 455.6 | 439.5 |
| `metal`，标签升序 | 800.7 | 783.9 | 568.7 |
| `metal`，1–10 秒时长筛选 | 1,049.3 | 1,027.2 | 925.8 |

5.6 秒异常未在这三次复核中重现，**原因尚未归因**；不能直接断言是 OS 缓存或后台任务。B 的时长筛选仅搜索本身仍需 **718.5–722.8 ms**，加目录统计为 **925.6–932.5 ms**。这说明仍存在可重复的长尾，存储瘦身不能替代查询路径的后续优化。

本次仅 **909,342** 条记录，未达到 1M；项目目标仍为 **P95 latency <500ms for 1M+ records**。尚不能以本报告宣布百万级发布门槛通过。

## 5. 修改、删除、回滚与重开

在两份可写隔离副本上，用同一事务适配器执行：

1. 20 条记录连续三轮更新标签和备注；B 每次显式更新全部 12 个 FTS 列。
2. 五条记录删除后回滚。
3. 五条记录正式删除。
4. 两端分别 FTS optimize、完整性检查、关闭连接和重新打开。

共七个检查状态均通过，且测试期间复用 DataProvider，覆盖外部提交后的读取缓存失效。每个状态比较完整命中和原生 BM25、完整 docsize、全局统计、结果 DTO 和目录统计；自定义 BM25 对原生最大误差仍为 0 ULP。

这是索引写入规则与读取路径验证，**不是已经打通正式 Metadata、扫描、导入、服务端快照增量等所有入口**。本轮没有长时间持续 churn/空间回收试验，也没有把全库构建等同于逐条新增接口验收。

隔离 SQLite 3.54.1 构建另通过现有 `search_text::tests` 4 项、`search_bm25::tests` 18 项。没有修改应用源码，未执行正式整包构建、安装或宣称 workspace 全部测试通过。

## 6. 构建耗时与迁移空间

| 阶段 | 实测秒数 |
|---|---:|
| 固定来源的 backup | 38.21 |
| backup + 基线 SHA256 | 49.95 |
| 复制业务表、移除六列、复制对象 | 94.07 |
| 全库投影核对并建立 FTS | 115.21 |
| FTS optimize | 20.01 |
| VACUUM INTO | 23.75 |
| 索引构建至最终候选合计 | 178.73 |
| 完整业务/词项/SQLite 审计 | 80.62 |

复制业务数据与索引构建合计约 **272.8 秒**，不含来源备份、网络下载及后续所有一致性/性能检查。使用八个投影 worker，FTS 分批事务 5,000 行；这不是生产迁移停机时间承诺。

本轮未连续采样磁盘峰值，不能给出已验证的最低剩余空间。仅按本样本主文件计算：保留来源 19.50 GB、回滚备份 19.50 GB、整理前候选 10.61 GB、整理输出 10.50 GB，合计已约 60.1 GB，尚不含 WAL、临时排序和安全余量。生产规划器应区分“磁盘总占用”和“还需额外可用空间”，根据具体执行路线预算并在每个阶段复核；不能用最终库大小作迁移空间需求。

## 7. 迁移与版本交付状态

设计已明确：

- 同次发布的桌面、CLI、服务端共享 workspace 版本；允许范围内的已部署版本可不同步升级。
- 内置兼容目录分别声明无需迁移的发布范围、可自动迁移的来源范围、实际读/写格式和迁移图；最终按数据库实际能力判定。
- `compatible` / `migratable` / `rebuild_required` 三种处置；全量重建必须有专门检查证据，不按主版本号强制触发。
- 共享 Rust 迁移核心由客户端和服务端内置，提供 inspect、plan、apply、resume、verify、rollback；源库、权威服务端库与客户端缓存由正确所有者执行。
- 维护锁、回滚备份、已提交进度、恢复协议、旧 rev 3 进行态识别、下载前兼容拒绝及缓存保留。

**这些是下一版契约，尚未成为已发布的工具。** 本次实验验证 v5/rev3 → B 的全量数据路径；schema 3/4、旧 tokenization、旧迁移恢复、未知 feature、两端不同版本协商、服务端权威库升级、断电/磁盘不足、正式替换和回滚仍须实现并通过矩阵测试。由于实测仍有长尾且样本不足百万，本轮支持继续应用实现，不支持直接替换工作库。
