# Schema v6 与方案 B 的合并升级契约

状态：2026-10-21 候选实现与隔离验收完成，未发布。交付为草稿 PR；首次排序退化的复现与后续修复见下文，不构成合并、部署或正式 release 批准。

## 目标与边界

先完成方案 B 的 CR，修复迁移数据安全、断点恢复、回滚和客户端/服务端兼容问题，整理到现有草稿 PR，不合并、不部署、不发布。当前安装和工作库不变。

随后实施已定稿的 v6 结构方案：播放历史仅存客户端本机，主库删除 `play_history`、`audio_files.play_count` 和 `audio_files.last_played_at`。其他用户字段、未知 Metadata 和扩展结构均保留；没有逐项授权的字段不得删除。结构升级与 B 的搜索存储转换合并为一次受保护的候选库发布，避免对 90 万行反复重写。

## 对现有迁移器的评估

现有内置迁移器具有来源绑定、完整备份、分批复制和索引断点、候选库验证、原子发布及受保护回滚，可作为执行器。不能直接照抄旧方案中的原地 DROP SQL：当前 B 会重建业务表并重建 FTS，应复用同一套声明式退役和保留投影校验。备份、恢复任务和格式身份继续绑定实际编译步骤。

新增的必需工作是：退役最后播放时间；引入独立本机历史；将本地旧历史导入置于完整备份后、主库变更前；区分本地权威库、服务端权威库和远程快照；更新 JSON、attributes、导出、客户端 UI 和两端兼容测试。

## 历史与安全顺序

历史位于 `<data_root>/play-history/<safe_library_id>/history.db`，独立 WAL、`user_version=1`，默认每库 5000 行，配置 `play_history_limit=0` 禁止新记录。不累计次数。本地库使用 canonical 路径 SHA256 的 `local-` 命名空间，数据库原路径上的版本更新保持身份不变，手动移动数据库文件另起历史范围；服务器库使用 `server-<library_id>`，防止两类身份碰撞。目录名采用完整 UTF-8 字节的无填充小写 base32 安全编码，支持服务端 128 字节 ID，无截断。两种客户端模式都使用本机存储，不上传或下载播放历史；快照替换及缓存清理不包含此目录。

本地库升级顺序：验证来源与独占权限 → 生成并验证完整备份 → 从只读备份幂等导入旧历史，提交记录和导入标记 → 安装主库维护保护 → 执行候选转换和验证 → 原子发布。历史导入失败必须在主库安装保护或结构变更前失败；重试不能重复导入。服务端库、快照、恢复暂存副本均不能触发本地历史导入。已有回滚备份和任务不自动清理。只读来源的本地导入先验证路线、发布身份明确的旧格式自有副本，再在最终路径运行这套持久迁移；失败可留下可恢复的旧格式目标与任务，禁止另一来源覆盖。导入的独占目标锁和所有普通打开/新建的共享或创建锁覆盖此窗口；发布前同步本地归属意图，崩溃后仍阻止无本地历史上下文接管。显式 CLI 迁移命令同样校验已有归属意图，不为只读计划创建新 sidecar。未知或损坏意图阻断，不按空意图处理。

客户端播放历史写失败仅报告 diagnostics，不阻塞音频线程。Stop/Ended 后再次 Play 是新记录，暂停/恢复、seek、变速和 repeat 不重复记一次播放会话。历史清空须确认，只清当前 library_id，并绑定来源 generation。历史素材定位按库、ID 和记录路径共同判断；恢复其他库造成同 ID 异路径时不得误选另一个声音，允许按历史路径兜底。历史保留的是事件发生时的路径；合法 relink 后旧路径已消失时，这些旧事件也可能显示缺失，避免仅凭复用的 ID 误选声音。

## 格式与两端兼容

v6 schema 数字保持 6。此前未发布的 B 格式 `ale-s6-cld1-t3-m2-p0` 保留 last_played_at，不能复用其格式 ID 声称新契约。新版格式为 `ale-s6-cld1-t3-m2-p1`，`play_history_retired=2`；实际检查三个退休对象均不存在。p0 只读兼容并可通过 owned 候选迁移，未知未来 feature 拒绝写入。

新客户端保持读取 schema 3–6，SQL 不引用删除列。旧服务端 JSON 中的 play_count 被忽略；新版响应不再输出该字段，attributes 不再输出 last_played_at，CSV 不再导出 play_count。旧播放路由保留原身份和参数校验并返回无写入结果，历史路由返回空数组。

正式部署顺序先客户端后服务端，另行申请维护窗口；本任务不执行部署。两端程序范围、协议、完整格式、快照身份和 revision 的既有校验必须继续生效。p1 实际库修改要求有效现代目录且客户端能读取服务器当前完整格式，在写入前拒绝缺失目录或只支持旧格式的客户端；只读播放兼容路由继续保留。旧客户端拒绝高于能力的库并提示升级，不修改文件；版本差异本身不构成必须重建。

## 首次排序修复与补充验收（2026-10-21）

最终查询源码 `a65e102`，程序仍为 `0.6.0-dev.1`。本轮仅修改读取/排序计划和相关验证，不新增索引、不改变 schema、FTS5 格式或分词修订，不执行迁移、合并、部署、打包或安装。数据库输入均为上轮已验证副本再复制到自有本地 NVMe 目录；当前安装和工作库没有参与。

### 原因与查询约束

原生 SQLite 3.54.1 的 EQP/VDBE 和分段计时将额外成本定位到 `FTS MATCH → 每个命中按主键读取 audio_files 排序键 → top-N` 路径。`metal` 命中 85,996 行；原路径即使只返回 200 行，仍要读取全部命中的主表键。原生诊断中 p1 采样率排序页 2,128.63 ms，已有采样率覆盖索引的独立查询为 109.89 ms，完整 DTO、键及 ID 顺序一致。诊断按 fts_join_visible → fts_join_all → numeric_covering 执行，每个变体内部按 COUNT → DTO 页 → 窄页执行；后执行的覆盖查询可能被前序读取预热，不据此计算严格冷盘加速倍数。去掉 `missing=0` 没有消除逐行主表读取；关闭 mmap 的独立复测反而更慢。这里没有测量硬件 I/O/page-fault 计数，不能进一步断言某个 overflow 字段或 OS 缓存机制就是唯一原因。

修复让完整 MATCH 集合通过非相关 IN 或一次物化参与覆盖索引查询，只在选定页面后按主键读取完整 Metadata。同快照计数、可见性、分页和取消机制保留，排序方向及 ID 升序同值规则不变。

| 排序 | 复用的现有索引 | 额外约束 |
|---|---|---|
| duration / sample_rate | idx_duration / idx_sample_rate | 验证单列、非 partial、正确列；All 可使用 |
| modified | idx_audio_visible_modified | 精确 DDL、Present；SQL 明写 missing=0 |
| channels | idx_audio_visible_format | 精确 DDL、Present；覆盖读取后仍做 top-N，不能假设 channels 天然有序 |
| tags | idx_audio_visible_tagged_folders | 精确 DDL、Present、derived tags ready、source_tags_text NOT NULL 且继承 BINARY collation；对完整 MATCH 左连接匹配标签键，为省略的空标签补空键；两级排序均显式 NOCASE |

覆盖计划只用于非空查询、无目录范围、无额外筛选且具有同快照 `no_missing` 证明的请求；命中范围为 16,384–2,097,152。Tags/Channels 另限 **131,072** 命中：前者会额外物化键并建立临时 ID 查找，后者的索引第一列是 bit_depth，无法按 channels 提前停止。预算外、缺失/错误索引、NULL 来源键、RTRIM/自定义来源 collation、无 derived 状态或不满足可见性证明时执行原完整查询。标签推导适用于 DTO 的 TEXT/NULL 用户标签域；非法 BLOB 标签不作为合法数据一致性结论。Filename 和 Relevance 的既有路径保留。

### 首次排序退化的历史基线

真实库首轮页面与目录合计 P95 为 466.80 ms，但存在明显的首次排序退化。按问题 case 分别启动新的只读进程/provider、先执行一次再重复两次，在同一 E: NVMe 上复测得到：

| 查询 / 排序 / offset | v5 首次合计（ms） | p1 首次合计（ms） | p1 第 2/3 次合计（ms） |
|---|---:|---:|---:|
| `metal` / `sample_rate` / 0 | 446.15 | 2510.32 | 358.96 / 436.60 |
| `metal` / `tags` / 0 | 799.86 | 1692.48 | 369.37 / 369.75 |
| `door` / `duration` / 200 | 108.03 | 547.76 | 69.66 / 66.77 |

这些定点用例的结果、DTO 和目录摘要仍相同；重复请求较快，首次成本可重现。主目标仍为 **P95 latency <500ms for 1M+ records**，P95 达标不代表每次请求均小于 500 ms。该轮没有修改查询实现，也没有实测定位底层成本。后续排序修复、原生计划证据和实际旧程序对照见上文补充验收；历史样本保留，不用后续缓存更热的样本覆盖。当前 PR 继续保持草稿且不部署。

### 百万条与服务端测量

合成库为 1,000,000 行。26 个 case 各新建一个 provider，仅测一次首次搜索随后首次目录聚合；打开、搜索、目录及顺序合计的 P95 分别为 25.26 / 342.53 / 91.43 / 405.21 ms。合计不含 provider 打开时间；目录可能复用刚完成搜索产生的状态。首次搜索达到报告中的 <500 ms 门槛，顺序合计达到报告中的 <500 ms 门槛。

随后共享 provider 执行 100 次混合重复请求，搜索及目录顺序合计的 P50/P95 为 27.35/227.13 ms；共享 provider 首轮 P95 为 364.56 ms。合成 benchmark 使用排序后零起点 `ceil((n-1)*p)`，与上表及 Router 的 nearest-rank 不同。fresh-provider 阶段前已执行共享 provider 的统计读取，OS 页缓存未控制；这不是 `--first-only` 的无预统计条件，也不是独立冷进程或冷磁盘测量。

服务端在同一 AppState/Router 上，首次 `/library`（无统计 sidecar/后台预热）33.79 ms，随后 100 次串行缓存请求 P50/P95/max 为 1.61 / 1.97 / 2.21 ms（nearest-rank）。计时包括 middleware、handler、JSON 序列化和 body 收集，不包含网络延迟或测试侧 JSON 解析。统计 sidecar 在首次后保持不变。

2 次旧播放兼容请求和空历史响应均不改变业务 revision 或 observer data_version，响应没有计数及最后播放时间字段。这里的不变性窗口为服务端启动后至请求结束、优雅退出 checkpoint 之前。

实际旧二进制 `AudioLibCli 0.5.0` 仅证明：显式打开该 v6 副本时拒绝，主库字节哈希不变，未留下 SQLite 写 payload。它不证明旧客户端能解码新服务端 DTO 或完成全部远程交互。
